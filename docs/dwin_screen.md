# DWIN screen, curve display and language notes

Detail moved out of `CLAUDE.md` to keep it short. `CLAUDE.md` keeps the invariants that matter when adding or changing a screen control ("DWIN Screen" section); everything else about the screen protocol, the VP map, the curve widgets and the language table is here. Trust the code if they disagree.

## Curve Display

`curve_display.c` plots a real-time curve on the DWIN screen. The active path is **dual-channel**: `CURVE_DrawRefFixed(raw, count, mul_x100, repeat)` pre-fills CH1 with the selected **preset pump-frequency curve** (integer gear values, `Y = raw * mul_x100 / 100`), then `CURVE_DualAppend(real_hz, 0)` appends one point per 250 ms to CH0 (real pump frequency). CH1 never changes after the pre-fill: when a knob-extended recording runs past the preset's end, the preset curve simply ends at its last point (the old zero-padding of CH1 was removed 2026-10-27 at the user's request). Every curve-page KEY1 clears CH0 (`CURVE_ClearChannel(CURVE_CH0)`), so a second brew without leaving page 4 starts again at X = 0 instead of continuing after the previous curve. `mul_x100 = 1250` maps gear -> Y (gear 40 -> Y 500). Pre-fill is redone whenever the curve page is entered or the 0xD250 knob changes slot. The legacy single-channel `CURVE_Update(temp, target)` / `CURVE_UpdatePressure(bar)` path still exists. Auto-sampling interval configurable 500-2000 ms, pause/resume, history replay.

X scale: `Curve_ApplyXStep()` sets 4 px/point (200 points = 50 s visible) or 2 px/point (400 points = 100 s) on both curve widgets (SPs 0xC000 = CH0 actual, white; 0xC010 = CH1 preset, green; both span X 103–903) and rewrites the axis labels (0xD254–0xD278). It is the only place the step is set, so the two curves always share one step — keep it that way. The step is chosen from the preset length (> 200 points → 2) and switched once from 4 to 2 when CH0 passes 200 points. It must be applied before CH1 is pre-filled, otherwise the pre-filled segment is drawn at the old step.

## DWIN Screen Communication

- **Screen**: DMG40960F040_01WTC (T5L, DGUS II) on USART2 PA2/PA3, 115200 (USART1 PA9/PA10 with `UART_SWAP`).
- **Frames**: `5A A5 [len] [cmd] [data...]`, no checksum. Commands `0x80/0x81` register write/read (general registers only), `0x82` write VP, `0x83` read VP / auto-upload, `0x84` curve data, `0xA3` music, `0xA5` picture. System VPs via 0x82: page `0x0084` (`5A 01 page_H page_L`), backlight `0x0082`, buzzer `0x00A0` (value × 8 ms; `DWIN_BuzzerPlayOnce` writes 0x000D = 104 ms).
- **Dispatch**: the USART ISR is a byte state machine that assembles each frame in `g_recv_frame` and copies completed frames into a 16-slot queue (`g_fq`; the screen's `5A A5 03 82 4F 4B` write ACKs aren't queued). `DWIN_ProcessRecvFrame()` (main loop) drains the whole queue each call and hands **every** 0x83 frame — poll replies and auto-uploads alike — to `on_vpread(vp, value)` in main.c, which routes by VP address into `*_resp` / pending flags consumed by the poll helpers. VPs that match nothing go to the language module if they equal its pending SP read. `g_last_read_vp` is bookkeeping only; it does not gate routing.
- **RX parser resync**: the ISR is a byte-wise state machine (`DWIN_USART_IRQHandler`). Long interrupt-off windows (Flash writes) overflow the 1-byte USART receive buffer and a lost byte corrupts the frame's `len`, after which the parser would swallow the following frames as "data". Two guards: an overrun (ORE) drops the half-received frame (gotcha 7), and a full `5A A5` header seen inside the data area restarts parsing at LENGTH. A lone `0x5A` is ordinary data — values like 90 (`0x005A`, the default brew temp) are common. The earlier rule "any 0x5A aborts the frame" dropped that frame plus the next one, and the screen doesn't resend.
- **Momentary controls are edge-triggered**: the screen re-reports values, so 0xD218, 0xD22C, 0xD080 and the page-12 buttons act only on a 0→1 transition; the MCU writes 0xD218, 0xD080 and the page-12 VPs back to 0 afterwards (0xD22C is not written back). Use the same pattern for new buttons — level-triggered handling re-fires on every re-report. **When the MCU writes a VP back to 0, reset its edge detector to 0 as well** (as the page-12 dialog does): the detector otherwise still holds 1 and swallows the next report of 1. 0xD218 is a page-1 increment control looping 0↔1, so without the reset (fixed 2026-10-27) re-entering the curve page took three taps (1 swallowed → 0 → 1).
- **Screen project**: `..\dgus\DWprj.hmi` (sibling folder of this repo). `DWIN_SET\13TouchFile.bin` holds the touch controls — a 16-byte header (page, area, target page, key code `0xFExx`, low byte = control type, e.g. 02 increment, 05 key return, 08 sync return, 0D bit control) followed by 16-byte parameter blocks starting with `0xFE` + VP. Parse it to check how a control reports before writing its handler.
- **Text**: `DWIN_SetText(vp, utf8)` converts UTF-8 to GBK through the table in `dwin_uart.c`; a character missing from the table is silently dropped. On this DGUS project a text control's **data VP = its SP (descriptor) + 0x6000** (e.g. SP 0x8A00 → data 0xEA00); writing to the SP corrupts the descriptor. For a new text control, ask the user for the data VP (or read the SP at runtime as `language.c` does).
- **VP map (main ones)**:
  - MCU → screen: 0xD004 boiler temp, 0xD008 pressure, 0xD010 head temp (floats), 0xD00C brew seconds (u16), legacy 0x2000 temp / 0x2002 heater % / 0x2006 pressure / 0x2007 pump % (still written each second; 0x2001/0x2003–0x2005 were only fed by the removed `brewing_process` and are no longer written), pre-infusion text 0xEA00/0xEA40/0xEA80 (`"dur/stop"`, `"0/0"` when disabled).
  - Screen → MCU: 0xA000 boot animation, 0xD000 boiler cycle, 0xD100–0xD118 navigation (pages 5–11), 0xD218 curve page, 0xD250 preset slot, 0xD300 leave curve page, 0xD304/0xD308/0xD30C save dialog, 0xD04C/0xD050/0xD054 light, 0xD22C cup reset, 0xD080 factory reset, plus the settings VPs listed under Settings.

## Language (`language.c`)

0xD060: 0 = CN, 1 = EN. `g_text[]` maps each text SP (0x8000–0x8880 from `文本映射表.txt`, plus the page-12 texts 0x8940/0x8980/0x89C0) to a CN/EN string. At boot the module reads each SP in turn — the reply is that control's data VP — and caches it, re-sending a read that gets no reply within 300 ms. Once all are cached it writes one string per `Language_Poll` call whenever 0xD060 differs from the applied language. It also recolors text on value changes (`g_color_rules[]`, e.g. 0xD22C → SP 0x8700). Keep `language.c` saved as UTF-8 with BOM (ARMCC must read the Chinese literals as UTF-8).
